# 018 — A rail, and five things that fold away

## What was asked

> okay, it's cleanenr now, but I'd like each section to be able to be collapsed,
> and a menu on the left for easy navigation.

## Spec 017 rejected both of these, and that is not a contradiction

017 listed "collapsible sections instead of fewer sections" and "a settings
sub-navigation" under alternatives rejected. The operative word was *instead*.
Nine cards behind nine disclosure triangles is nine decisions plus a tap each,
and a sub-nav to reach nine cards is machinery covering for bad grouping. On
five well-grouped sections both become what they should have been: a way to
shorten a screen that is already correctly organised, and a way to skip to a
part of it.

## The two constraints that shaped this

**The app is 640px wide.** `.app` is capped at `--content-max` and centred, at
every viewport, per NFR-07 ("iPhone portrait first, usable on desktop"). There
is no room beside the content for a rail without a screen breaking out of the
shell.

**There were no width breakpoints.** The only `@media` in 1,577 lines of CSS
was `prefers-reduced-motion`. A desktop rail is the app's first responsive
branch, which is a thing to do deliberately rather than discover later.

Ryan chose the rail on desktop with a chip fallback on phones, knowing it
costs both. So:

- Settings, and only Settings, widens to `--settings-max` (900px) at
  `min-width: 900px`, via `.app:has(.settings-layout)`. The shell does not
  need to know which route is mounted.
- 900px is the rail **plus** a content column still no wider than
  `--content-max`. The settings never get longer lines than the rest of the
  app; they gain a rail beside them.
- Below the breakpoint the same nav is a sticky horizontal chip row.

## One DOM, two shapes

`SettingsNav` renders one list. CSS turns it into chips or a rail. Rendering
two trees and hiding one would put the same five buttons in the accessibility
tree twice.

**They are buttons, not links.** The app runs on `HashRouter`, so the URL hash
*is* the route: `<a href="#account">` navigates to a route called `account`
rather than scrolling. Scripted scrolling here is a constraint, not a
preference, and the code says so where a reader would otherwise assume
laziness.

**Expand first, then scroll.** A collapsed section is a 48px strip. Scrolling
to it and expanding afterwards lands the viewport in the wrong place and the
section grows away underneath. A `requestAnimationFrame` waits for React to
commit the open state so the element has its full height to scroll to.

## Native `<details>`, not a div with a click handler

It gives keyboard operation, the correct screen-reader announcement, and
find-in-page that can open a *closed* section to reveal a match, with no code.
A hand-rolled disclosure has to earn each of those back and usually only earns
the first.

The heading sits inside the `<summary>` so the title is still an `h2` in the
document outline. The other way round makes the disclosure control *be* the
heading, which most screen readers read as "Account, heading level 2, summary".

The marker is drawn from a rotated border rather than a `+`/`–` glyph, so it
does not depend on the font having the character and does not shift baseline
between the three themes. It honours `[data-reduced-motion='true']`.

## Independent disclosures, not an accordion

Opening Theme to compare two of them should not fold away the sync status you
opened Settings to read. State is a `Set`, not one id.

On arrival: **Account open, the other four closed, not remembered.** Every
visit looks the same, there is nothing stored per device, and the thing most
often wanted is already open. `SETTINGS_SECTIONS` owns that default, and both
the nav and the panels are generated by walking that one list, so a section
cannot exist in one and not the other.

## Deliberately not built

**Scroll-spy.** With four of five sections collapsed the screen is roughly one
screenful, so a "currently viewing" highlight would flicker between sections
that are all visible at once, for an IntersectionObserver's worth of code.

**Remembered open state.** Offered and declined: the screen would look
different every visit, and the state would be per-device rather than synced.

## Acceptance criteria

1. Five sections, all collapsible, Account open on arrival. ✅
2. Desktop ≥900px: Settings widens to 900px, nav is a left rail, no other
   screen changes width. ✅ measured 900px, `176px 668px` grid
3. Below 900px: 640px cap restored, nav is a sticky horizontal chip row, no
   horizontal page overflow. ✅ measured at 390px, select still 324px wide
4. A nav click expands its section and scrolls to it, without closing
   anything else. ✅
5. Scrolling honours reduced motion, via the existing
   `usePrefersReducedMotion()`. ✅
6. Every CSS custom property referenced exists in `tokens.css`. ✅ checked
   individually after two (`--color-bg`, `--color-text-muted`) turned out not
   to exist and were silently falling back to nothing.

## Requirements touched

PRD 7.2, 7.4, 7.5 (settings screen), NFR-06 (accessibility), NFR-07
("iPhone portrait first, usable on desktop" — this is the first screen to use
the second half of that sentence).
